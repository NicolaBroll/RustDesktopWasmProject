# UI languages (i18n)

Everything the program shows is in **English**: UI (texts in
[Fluent](https://projectfluent.org/), step S31b), CLI, MCP, command catalog, errors, warnings,
journal entries, log and backup messages. The whole repository is English too: program text,
code comments, test names and fixtures, docs. Italian exists only as a second Fluent language
(`locales/it/*.ftl`, the only place where Italian is allowed): it is chosen in the "Settings…" window
(S49: as the system / Italiano / English, the system language through `Platform::system_language`,
English when unknown) and must be kept aligned. UI tests run in English (the `test-italiano` feature no longer
exists).

## Crates and files

- `crates/i18n` = `project-i18n` (L0, no project crate): `Lang` (`It`, `En`),
  `I18n` (texts of a language: `tr`, `tr_args`, `has`), the active language
  (`set_lang`, `lang`, `current`, `get(lang)`) and the `tr!` macro.
- Texts in `crates/i18n/locales/{it,en}/<area>.ftl`, one file per UI area. `build.rs`
  includes with `include_str!` every `.ftl` it finds: a new area is
  just a new file in the two folders, no list to touch.
- Fluent's Unicode isolation is turned off (`set_use_isolating(false)`): egui would show the characters.
- Language: the `Settings` of `crates/ui/src/settings.rs` (eframe storage, key `settings`) call
  `set_lang` at startup and on every change; the texts change from the next frame.

## Keys

- Name `<area>-<what>` in kebab-case, the area is the file name: `merge-continue-button` lives in
  `merge.ftl`. Parameters `$name` in snake_case.
- One message per line (in Fluent a newline inside a value stays a newline). Whole sentences
  live in the `.ftl`: no pieces to paste together in code (word order changes between
  languages); for variants use one key per case or a selector.
- Plurals with the selector on the number: `{ $n -> [one] 1 file *[other] { $n } files }`.
- Quotes: «…» in Italian, “…” in English. Standard English git terminology (stage,
  commit, branch, cherry-pick, working tree...); the names of operations (merge, rebase,
  cherry-pick, revert) stay in the code, the same in both languages.

## Adding a text

1. The key in `locales/it/<area>.ftl` **and** in `locales/en/<area>.ftl`.
2. In code `tr!("area-what")` or `tr!("area-what", n = count, branch = name)` (with
   `use project_i18n::tr;`). The key is always a literal in the macro: no keys composed
   at runtime, no direct calls to `tr_args`. A parameter is `&str`, `String`, `&String` or
   a number.
3. `cargo test -q -p project-i18n -p project-ui`: same areas and keys in the two languages, every
   key starts with its area, every file parses, every `tr!` of the UI (`crates/ui/tests/
   i18n_keys.rs`) has the key in both. A missing key stops in debug with a
   `debug_assert`; in release the key is shown.

## Migrating a module

- One area per function (`stash.ftl` for `stash.rs` and `view/stash_view.rs`): own files, so
  several agents work in parallel without conflicts. Only touch your own group of files.
- Every visible text (labels, hints, titles, status bar messages, errors
  composed by the UI) goes through `tr!`; the English text stays identical to before, so the existing tests
  do not change (in tests the language is English).
- A function that returned `&'static str` now returns `String`.
- Texts shared by several areas live in `common.ftl` (e.g. `common-wait`, `common-failed`), those
  of `lib.rs` and `executor.rs` in `app.ftl`.
- These stay in code: command ids, ref names, git text, `log::`, egui keys
  (`id_salt`), the language names in the menu (`Lang::native_name`).

## Engine errors

The errors of `EngineError`, the warnings (`warnings`) of results and the descriptions of
journal entries (S31c) do not carry an already composed text but a `Message` of
`project-engine`: Fluent key and parameters, created with the `msg!` macro and the literal key
(`msg!("engine-stash-gone", command = command, id = id)`), like `tr!`. A parameter (taken
by reference, trait `ToArg`) is a text, a number (chooses the plural), an `Oid`, a `RepoPath`,
another `Message` or an `EngineError` (translated into the same language); `MessageArg::Joined` joins
several messages (one line per ref of `UndoConflict`).

- `Display` of `EngineError` and of `Message` is English (CLI, MCP, log, tests). The UI uses
  `EngineError::text()` (active language) or `text_in(lang)`; `EngineError::message()` gives the key and
  parameters of every variant.
- In JSON (command results: `warnings`, `description` of journal entries, `next_undo`,
  `next_redo`) a `Message` is `{"text": <English>, "key", "args"}`: CLI and MCP read `text`, the
  UI decodes into the engine's typed results and calls `Message::text()`, which shows it
  in its language. It can also be read back from a plain string (text that stays as it is,
  `Message::plain`).
- Keys in `locales/{it,en}/engine.ftl` (the text of every variant, names, paths, notes) and
  one area per function: `engine-branch`, `engine-commit`, `engine-conflict`, `engine-discard`,
  `engine-journal` (journal descriptions), `engine-lines`, `engine-merge`, `engine-pick`, `engine-pull`, `engine-push`, `engine-remote`,
  `engine-stash`, `engine-undo`.
- Git's text (`stderr`, `message`), paths and names stay parameters as they were; a git
  error with an explanation of our own around it is `EngineError::GitWithReason` (same
  `Display` as `Git`).
- Sentence pieces (`engine-busy-*` for "`command` would change branch", `engine-op-*`) are
  whole keys; the variants with a number or a case (`$operation`, `$untracked`) use
  selectors.
- `crates/engine/tests/i18n_keys.rs` reads every `msg!(` of `crates/engine/src` and
  `crates/git/src`: the key exists in both languages, every `$parameter` of the text is passed and
  every passed parameter is used; an `engine*` key that nobody uses is an error.

## What stays untranslated

These exist only in English (no Fluent key): CLI, MCP, titles and parameters of the catalog
commands, xtask, `log::` messages, `expect`/`panic`, commit messages and backup refs
(`project: backup of ...`), the texts of the `project-core` and `project-domain` errors
(`CoreError`, `DomainError`: L0/L2, they do not import `project-i18n`; they arrive inside
`engine-other`), the simulated `stderr` of the `MemoryBackend` and the sample repo data. Git's text
(`stderr`) stays as it is.
