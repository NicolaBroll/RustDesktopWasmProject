# Lingue della UI (i18n)

L'app egui è in **italiano e inglese** con [Fluent](https://projectfluent.org/) (step S31b).

## Crate e file

- `crates/i18n` = `project-i18n` (L0, nessun crate del progetto): `Lang` (`It`, `En`),
  `Lang::from_locale`, `I18n` (testi di una lingua: `tr`, `tr_args`, `has`), la lingua attiva
  (`set_lang`, `lang`, `current`, `get(lang)`) e la macro `tr!`.
- Testi in `crates/i18n/locales/{it,en}/<area>.ftl`, un file per area della UI. `build.rs`
  include con `include_str!` tutti i `.ftl` che trova (funziona anche in wasm): un'area nuova è
  solo un file nuovo nelle due cartelle, nessun elenco da toccare.
- Isolamento Unicode di Fluent spento (`set_use_isolating(false)`): egui mostrerebbe i caratteri.
- Lingua iniziale: quella salvata (`eframe::Storage`, chiave `lingua`), altrimenti
  `Platform::locale()` (`sys-locale` sul desktop, `navigator.language` sul web; `it*` → italiano,
  il resto → inglese), altrimenti italiano. Il menu a destra della barra in alto la cambia subito;
  i testi già composti (es. un messaggio nella barra di stato) restano nella lingua di prima.

## Chiavi

- Nome `<area>-<cosa>` in kebab-case, l'area è il nome del file: `merge-continue-button` sta in
  `merge.ftl`. Parametri `$nome` in snake_case.
- Un messaggio per riga (in Fluent l'a capo dentro un valore resta un a capo). Le frasi intere
  stanno nel `.ftl`: niente pezzi da incollare nel codice (l'ordine delle parole cambia tra
  lingue); per varianti si fa una chiave per caso o un selettore.
- Plurali con il selettore sul numero: `{ $n -> [one] 1 file *[other] { $n } files }`.
- Virgolette: «…» in italiano, “…” in inglese. Terminologia git inglese standard (stage,
  commit, branch, cherry-pick, working tree...); i nomi delle operazioni (merge, rebase,
  cherry-pick, revert) restano nel codice, uguali nelle due lingue.

## Aggiungere un testo

1. La chiave in `locales/it/<area>.ftl` **e** in `locales/en/<area>.ftl`.
2. Nel codice `tr!("area-cosa")` o `tr!("area-cosa", n = count, branch = name)` (con
   `use project_i18n::tr;`). La chiave è sempre un letterale nella macro: niente chiavi composte
   a runtime, niente chiamate dirette a `tr_args`. Un parametro è `&str`, `String`, `&String` o
   un numero.
3. `cargo test -q -p project-i18n -p project-ui`: stesse aree e chiavi nelle due lingue, ogni
   chiave comincia con la sua area, ogni file si analizza, ogni `tr!` della UI (`crates/ui/tests/
   i18n_keys.rs`) ha la chiave in tutte e due. Una chiave mancante in debug ferma con un
   `debug_assert`; in release si vede la chiave.

## Migrare un modulo

- Un'area per funzione (`stash.ftl` per `stash.rs` e `view/stash_view.rs`): file propri, così
  più agenti lavorano in parallelo senza conflitti. Si tocca solo il proprio gruppo di file.
- Ogni testo visibile (etichette, suggerimenti, titoli, messaggi della barra di stato, errori
  composti dalla UI) passa da `tr!`; l'italiano resta identico a prima, così i test esistenti
  non cambiano (nei test la lingua è l'italiano).
- Una funzione che restituiva `&'static str` ora restituisce `String`.
- `WAIT` di `view.rs` diventa `wait()`; la costante si toglie quando nessuno la usa più.
- Restano nel codice: id dei comandi, nomi di ref, testo di git, `log::`, chiavi di egui
  (`id_salt`), i nomi delle lingue nel menu (`Lang::native_name`).

## Cosa resta non tradotto

CLI, MCP, descrizioni dei comandi del catalogo, documenti, testo di git (`stderr`), voci del
diario (le descrizioni di undo/redo vengono dal motore). Gli errori del motore (`EngineError`)
restano in italiano fino a S31c, che darà loro una chiave e i parametri.
